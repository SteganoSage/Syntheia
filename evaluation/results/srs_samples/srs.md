### 1.2 Scope

The system will automatically categorize user transactions, generate monthly expenditure reports, allow users to set spending limits, send alerts when users approach or exceed their budgets, analyse user spending patterns, suggest ways to improve financial management, store user transaction history for at least 12 months, allow users to view and manage their alerts, handle cases where users' external bank accounts are unavailable or unconnected, and provide a user-friendly interface for users with visual impairments.

This specification states 28 requirements: 6 stated in the scenario, 5 implied by analysis of what such a system needs, and 17 proposed from the regulations and security controls that apply to it. Section 3 gives each one with its origin.

Business objectives stated in the scenario:

- help users manage their income and expenses (“The system should automatically categorize transactions, generate monthly expenditure reports and allow users to set spending limits.”)
- analyse spending patterns and suggest ways to improve financial management (“The system shall analyse user spending patterns and suggest ways to improve financial management.”)

The system will:

- Categorize Transactions — The system shall automatically categorize user transactions.

## Appendix E — Recommended development life cycle

**Recommendation.** Recommended model: Prototype.

> New product direction + Stakeholder involvement + Proof of concept -> Prototype

The project is a new product direction for the organization, and the stakeholders want to be involved in all phases of the life cycle. The Prototype model is the best fit for this project because it allows for a working model to be created quickly, requirements to be clarified by seeing them run, technical risk to be investigated before committing, and early feedback from real users to be obtained.

| Rank | Model | Fit | Matched / answered |
|---|---|---|---|
| 1 | Prototype | 91% | 10/11 |
| 2 | Agile (derived) | 64% | 7/11 |
| 3 | Spiral | 64% | 7/11 |
| 4 | RAD | 45% | 5/11 |
| 5 | Waterfall | 27% | 3/11 |

Why Prototype suits this project:

- A working model quickly: This project requires a proof of concept to demonstrate capability, as stated in the problem statement: 'The system should automatically categorize transactions, generate monthly expenditure reports and allow users to set spending limits.'
- Requirements clarified by seeing them run: The stakeholders need to see something working before they can say what they want, as evidenced by the fact that the problem statement describes what the system should do, but does not provide a complete list of requirements.
- Technical risk investigated before committing: The technical feasibility of the system is in doubt, as evidenced by the fact that the organisation is still working out what they want, which implies that they may not know if it can be built.
- Early feedback from real users: The problem statement mentions the system's features and user interactions, implying a feedback loop and user engagement throughout the life cycle.

**Trade-off.** Prototype assumes the system has to interoperate with systems outside itself — that is not the case here, so that part of its design earns nothing on this project.
